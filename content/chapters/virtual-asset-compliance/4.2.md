## 4.2 Implementing the Travel Rule

The Travel Rule is the most operationally complex crypto AML requirement. This chapter covers how VASPs actually implement it in production.

### The data requirements

For transfers above the threshold (typically USD/EUR/GBP 1,000), VASPs must exchange:

**Originator information** — name, account number (wallet address), physical address (or unique identifier), and for natural persons, date and place of birth where available.

**Beneficiary information** — same fields for the recipient.

For transfers below the threshold, VASPs must still collect the information but may not need to transmit it — though many jurisdictions require collection regardless.

### The technical challenge

Unlike SWIFT for bank transfers, crypto has no universal messaging network. VASPs must implement Travel Rule data exchange through:

**Travel Rule protocols** — technical standards for structured data exchange:

- **IVMS 101** — InterVASP Messaging Standard, the emerging global standard
- **TRP (Travel Rule Protocol)** — earlier standard, still in use
- **OpenVASP** — open-source Travel Rule directory and messaging framework
- **Notabene, Sygna Bridge** — commercial Travel Rule compliance platforms

**API integration** — VASPs connect to Travel Rule platforms that handle message formatting, encryption, delivery and receipt confirmation. The customer experience should be seamless: the VASP collects the required data at the time of transaction and the platform handles transmission.

### The unhosted wallet problem

Most crypto transactions involve at least one unhosted wallet — a self-custody address not controlled by any VASP. The Travel Rule cannot require data exchange with an entity that does not exist.

FATF's solution: VASPs must **collect and retain** information about unhosted wallet counterparty transactions above thresholds. This means:

- When a customer withdraws to an unhosted wallet, the VASP must collect the beneficiary's information (or document why it cannot)
- When a customer deposits from an unhosted wallet, the VASP should apply enhanced scrutiny — there is no counterparty VASP to vouch for the origin

Implementation varies: some jurisdictions require full originator/beneficiary data for unhosted wallets; others accept a "best efforts" approach; others are still figuring it out.

### Practical implementation steps

1. **Determine applicable thresholds** — varies by jurisdiction and customer type; build a rules engine that applies the correct threshold per transaction
2. **Integrate Travel Rule platform** — select a compliant messaging provider, implement API integration
3. **Collect customer data** — at onboarding and for each counterparty; store securely with appropriate retention
4. **Screen counterparty data** — check beneficiary information against sanctions lists before transmitting
5. **Handle failures** — what happens when the counterparty VASP does not respond or rejects the message? Policies for holding, returning or escalating transactions
6. **Audit and test** — regular testing of Travel Rule message flows, data quality checks, gap analysis

### Common failure modes

- **Incomplete data** — customers provide partial information; VASPs transmit incomplete messages that fail compliance
- **Threshold gaming** — customers split transactions to stay below thresholds (structuring in crypto)
- **Unhosted wallet avoidance** — customers route through unhosted wallets specifically to bypass Travel Rule data exchange
- **Stale data** — customer information changes but VASPs do not update their records
